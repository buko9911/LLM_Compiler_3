## 패킹은 타당하지만 적용 조건이 있다

행 우선 FP16 [4096][4096]의 256열 패널은 512 B × 4096행이다.
패널 순서 [N/panel][K][panel]로 이미지 자체를 재배열하면 2,097,152 B × 1행으로
전송할 수 있다. 전송량은 같다. 단순히 GDMA의 rows만 1로 바꾸면 잘못된 값을 읽는다.
`Graph.cpp`의 패킹 표시, `Lower.cpp`의 패널 주소 계산과 연속 전송 병합,
`plena-compile.cpp`의 이미지 변환이 함께 이 계약을 구현한다.

수정한 문제:

- 내장 상수는 이미지 작성 시 전치·패킹 경로를 건너뛰었다. 이제 외부 입력과
  같은 변환을 적용한다. 상수 메타데이터 자체는 논리적 원소 순서를 유지한다.
- 이미지 입력 크기를 무조건 FP16으로 검사하던 부분은 dtype의 원소 폭을 사용한다.
- 패널 축을 바꾸는 reshape나 물리적 레이아웃을 유지하지 않는 copy 사용자가
  있는 인자는 자동 패킹 대상에서 제외한다.
- 패킹된 subview의 끝 경계를 검사한다. 여러 패널을 일반 행 우선 버퍼처럼
  복사하려는 경로는 오류로 처리한다. 전체 너비가 한 패널이면 일반 연속 버퍼다.

## Local DMA와 버퍼

기존 lowering은 L2_LOAD_STRIDED / L2_STORE_STRIDED를 사용했다.
이제 비동기 변형을 발행한다. 현재 시뮬레이터의 `accelerator/dispatch.rs`는
L1 주소 범위별 load 완료와 store capture 의존성을 추적한다. L2에서 겹치는
RAW/WAR/WAW 접근은 컴파일러가 C_WAIT_LDMA로 정렬한다. 코어 블록 종료의
C_FENCE_ALL과 전역 스케줄러에 제공하는 L2 접근 범위는 유지한다.

M_LOAD는 L1에서 별도 MatrixOperandSnapshot으로 데이터를 읽는다. 따라서
계산 시간 전체에 걸쳐 원본 L1 바이트를 붙잡는다는 가정은 맞지 않는다.
이 변경은 기존 버퍼에서 독립 명령의 진행을 허용한다. 다음 타일의 사전 적재를
앞당기는 소프트웨어 파이프라인이나 L1 더블버퍼를 구현한 것은 아니다.
활성값은 여전히 코어 구간 안에서 재사용하고, 패널 간 영구 상주는 구현하지 않았다.
4 MiB 용량만 보고 상주를 결정할 수는 없다. 다른 활성값, 가중치, 출력의 수명과
코어별 복제, 주소 재사용까지 함께 배치해야 한다.

## 제시된 성능 설명에서 고쳐야 할 부분

- 32×4096 FP16은 262,144 B = 256 KiB다. 64번이면 16 MiB다.
  MB와 MiB를 혼용하면 비용 계수가 달라진다.
- 두 실행의 전송량을 MiB로 해석하면 선형 적합은 약 0.026086 cycles/B,
  51.981 cycles/row이고, 역수는 38.334 B/cycle이다. MB라면 36.558 B/cycle이다.
  둘 다 32 B/cycle보다 크므로, 이를 해당 링크의 실효 처리량이나 물리적 상한으로
  확정할 수 없다. 두 점은 대기·주소·동시성 효과를 분리하지 못한다.
- 8192 전송 사이클 대 4096 연산 사이클은 한 배열에 32 B/cycle를 공급하고,
  가중치를 한 번만 사용하는 이상화된 계산이다. 완전히 직렬이면 계산 비중은
  1/3, 완전히 겹치면 최대 1/2이다. 실제 시뮬레이터에는 wavefront 61사이클과
  피연산자 적재·writeout도 있다. Matrix engine 이벤트 전체가 순수 MAC 시간은 아니다.
- 4코어를 분석할 때 NoC 32 B/cycle가 어느 공유 자원의 대역폭인지 확인해야 한다.
  코어 하나의 상한을 전체 코어의 평균 활용률이나 이벤트 합집합에 그대로 적용하면 안 된다.
- 이벤트 duration 합계, 같은 레인의 구간 합집합, 모든 코어의 합집합은 서로 다르다.
  Core command stream에는 기다리는 명령의 시간도 들어간다. 94.7%는 유효 연산
  활용률이 아니다. 이벤트 이름만으로 전체 대기 원인을 분해할 수 없다.
- seq=256은 가중치 재사용의 *기회*를 늘린다. 현재 루프가 각 M 타일에서 가중치를
  다시 올리면 L2→L1 트래픽은 줄지 않는다. 실제 상주/루프 순서 변경이 필요하다.
- 같은 자원 정의와 바이트 수에 근거한 하한은 대략 max(DRAM 시간, NoC 시간,
  계산 시간)이다. 이 값들만으로 20 M이라는 달성 시간 또는 절대 하한을 도출할 수 없다.
  중복 적재를 없애면 하한에 넣는 전송량도 다시 계산해야 한다.

## 검증

등록된 단위·lit·드라이버·시뮬레이터 테스트를 실행한다. 드라이버 회귀 테스트는
여러 패널을 강제한 비균일 상수 가중치의 실제 이미지 바이트를 독립적으로 검사한다.
행렬곱 통합 테스트는 4코어, 6 KiB L1에서 K 분할과 버퍼 재사용도 검증한다.

4코어 FP16 matmul M=32, K=1024, N=512, 동일 시뮬레이터 설정에서:

| 항목 | 기존 blocking | async |
|---|---:|---:|
| 전체 사이클 | 144,912 | 142,185 |
| PyTorch FP32 matmul → FP16 비교 | 비트 일치 | 비트 일치 |

약 1.9% 감소이며 Llama 전체 층에 대한 개선율 추정치는 아니다.

동일 캡처로 실행한 Llama-3.1-8B 디코더 한 층, prefill 32토큰, 4코어의 최종 결과:

| 항목 | 기존 blocking | 최종 async + L2 의존성 대기 |
|---|---:|---:|
| 전체 사이클 | 39,355,430 | 38,580,452 |
| 기존 출력과 비교 | 기준 | 비트 일치 |

**774,978사이클, 약 1.97% 감소**다. 검증된 PyTorch 참조 대비 최대 오차는
0.01880, 참조 최대 크기 대비 비율은 0.001449로 기본 허용 오차 안에 있다.
최종 출력은 이 검증을 통과한 출력과 비트 단위로 동일하다.
단순 비동기화만으로 20 M을 달성하지 못했으며, 더 큰 개선에는 적재를 앞당기는
스케줄과 중복 적재 제거를 별도로 설계·측정해야 한다.

실행 산출물은 `build/dma-review/llama/{before,final}`의 `timeline.json`,
`simulator.log`, `program.bin`과 `build/dma-review/llama/comparison.json`이다.
`package` 디렉터리는 PyTorch와 비교한 중간 실행이므로 최종 성능값으로 사용하지 않는다.
